# Спецификация интеграции React-интерфейса с системой «Кадровый заказ»

Дата фиксации контракта: 25.09.2026.

Документ предназначен для разработчика React-приложения из репозитория
`Daniil-opin/doc-bntu-front`, каталог `frontend`. Он описывает обязательные
изменения фронтенда и целевой JSON-контракт FastAPI.

На дату документа серверные страницы Jinja2 работают, но маршруты `/api/*`
ещё не реализованы. Команда бэкенда добавляет их параллельно с переделкой
React-приложения. Нельзя подменять указанные ниже JSON-маршруты существующими
HTML-маршрутами без `/api`: HTML-маршруты возвращают страницы или HTTP 303,
а не описанные здесь объекты.

Все значения в примерах соответствуют полям действующих моделей проекта.
Массивы в больших ответах сокращены до нескольких элементов, но каждый
показанный элемент приведён полностью по контракту.

## Изменения после демо 25.09

Этот раздел имеет приоритет над более ранними примерами документа.

### Статусность разделов спецификации

- **STABLE** — имена полей, URL и форматы зафиксированы. Можно писать код
  без дополнительных оговорок.
- **DRAFT** — имена полей и URL финальные, но серверные маршруты ещё не
  реализованы. Можно закладывать контракт в типы и интерфейсы, работать
  против моков, а затем заменить только источник данных.
- **REMOVED** — функциональность не реализовывать; упоминания в старых
  версиях документа игнорировать.

Совместимость со стороны сервера: поля STABLE-разделов не переименовываются
и не удаляются; изменения в них выполняются только добавлением новых полей.
Клиент должен игнорировать неизвестные поля JSON. Названия `date_start`,
`date_end` и `base_number` заменяют использованные в раннем черновике
`start_date`, `end_date` и составной `number` до реализации этих маршрутов.

### Краткий список изменений

1. Договор передаёт обязательный `date_start`, опциональный `date_end` и
   чистый `base_number` без номера или даты дополнительного соглашения.
2. При смене статуса заявки `comment` необязателен. Для договора и д.с.
   комментарий обязателен.
3. Договоры, д.с. и заявки используют только статусы `Активен`/`Закрыт`
   либо `Заявка`/`Закрыт` для заявки. Карточка организации не скрывает
   закрытые документы.
4. В строке заказа `profile` содержит свободный текст профилизации и может
   быть `null`.
5. Ответ карточки организации содержит `applications`.
6. Добавлены контракты статистики и экспорта.
7. Для `422` зафиксирован список ошибок по конкретным полям.
8. Генерация документов и реквизиты БНТУ не требуются.

## 1. Что исправить в React-приложении

### 1.1. Авторизация

#### `frontend/src/app/providers.tsx`

- **Сейчас:** пользователь определяется по `localStorage['bntu-auth']`, любой
  непустой пароль считается правильным, после входа создаётся локальный
  `demoUser` с ролью `ADMIN`.
- **Должно стать:** при запуске вызвать `GET /api/auth/me`; при входе отправить
  логин и пароль в `POST /api/auth/login`; хранить пользователя и его роль из
  ответа сервера. `localStorage` не является признаком действующей сессии.
- **Зачем:** автором изменений в журнале должен быть реально вошедший
  сотрудник.

Вызовы выполнять с `credentials: 'include'`. JWT и заголовок `Authorization`
не используются.

#### `frontend/src/pages/LoginPage.tsx`

- **Сейчас:** поля заранее заполнены `admin/admin`; вход выполняется локально;
  есть восстановление пароля по электронной почте.
- **Должно стать:** поля пустые; форма вызывает `POST /api/auth/login`;
  восстановление пароля и весь экран отправки письма удалить.
- **Зачем:** в модели пользователя нет электронной почты, сброс пароля
  выполняет администратор.

После успешного входа:

1. Если `need_password_change === false`, перейти на `/app/`.
2. Если `need_password_change === true`, перейти на
   `/app/change-password` и не открывать остальные защищённые страницы до
   успешной смены пароля.

#### Новый экран `/app/change-password`

- Поля: текущий пароль, новый пароль, повтор нового пароля.
- Минимальная длина нового пароля — 8 символов.
- Вызов: `POST /api/auth/change-password`.
- После успеха повторно вызвать `GET /api/auth/me`, затем перейти на `/app/`.

#### `frontend/src/shared/ui/AppShell.tsx`

- **Сейчас:** выход очищает только локальное состояние.
- **Должно стать:** вызвать `POST /api/auth/logout`, затем очистить локальное
  состояние, удалить оставшийся от прототипа ключ `bntu-auth` из
  `localStorage` и перейти на `/app/login`. После миграции не записывать
  признаки авторизации в `localStorage` повторно.
- **Зачем:** серверная сессия также должна завершиться.

#### `frontend/src/shared/api/client.ts`

- При любом ответе `401` очистить локального пользователя и перейти на
  `/app/login`.
- При `403` показать сообщение «Недостаточно прав для выполнения действия»;
  приложение не должно падать или считать операцию успешной.
- Не считать HTML после перенаправления успешным JSON-ответом. Для `/api/*`
  сервер возвращает JSON или `204 No Content`, но не HTML.

### 1.4. Решения, расходящиеся с моделью системы

#### `frontend/src/pages/UsersPage.tsx` и `components/users/*`

- Удалить кнопку, диалог и локальную логику удаления пользователя.
- Оставить создание пользователя и редактирование ФИО/роли.
- Удалить электронную почту из таблицы, форм, типов и профиля.
- Не добавлять блокировку/разблокировку: такой функции в минимальной версии
  нет.

Причина: пользователь является автором неизменяемых записей аудита, поэтому
его нельзя удалять.

#### Ролевой доступ

- Пункт «Пользователи» показывать только при `user.role === 'ADMIN'`.
- Пункт «Настройки» показывать обеим ролям: личный профиль и смена своего
  пароля доступны каждому вошедшему сотруднику.
- Руководитель (`HEAD`) видит организации, договоры, заявки и весь журнал.
- Даже при скрытом пункте меню обрабатывать `403`: скрытие не заменяет
  серверную проверку прав.

#### `frontend/src/pages/SettingsPage.tsx`: личный кабинет

Раздел `/app/settings` должен соответствовать двум областям:

1. **Профиль** — доступен обеим ролям. Получить данные из
   `GET /api/auth/me` и показать ФИО, логин и русскую подпись роли. Поля
   только для чтения: самостоятельное изменение ФИО, логина или роли здесь
   не предусмотрено. Электронную почту не показывать.
2. **Безопасность** — доступна обеим ролям. Кнопка «Изменить пароль» ведёт
   на `/app/change-password`; форма содержит текущий пароль, новый пароль и
   повтор нового пароля. Совпадение новых паролей React проверяет до запроса.
   Серверу передаются только `current_password` и `new_password`.

Вкладку «Реквизиты БНТУ», её форму, локальные значения и обращения к
`GET/PUT /api/settings` удалить. Эти маршруты не планируются: документы
приходят из АИС и системой не формируются.

Экран обязательной смены временного пароля использует ту же форму и тот же
`POST /api/auth/change-password`, но открывается сразу после входа, если
`need_password_change === true`.

В `DataTransferPage.tsx` кнопки экспорта пока скрыть или отключить: маршруты

### 1.5. Импорт Excel

Не устанавливать `Content-Type: application/json` глобально для всех

const headers = new Headers(init?.headers)
if (!(init?.body instanceof FormData) && !headers.has('Content-Type')) {

Для `FormData` браузер сам установит `multipart/form-data` с корректной

### 1.8. Формирование документов не требуется

Договоры, дополнительные соглашения и заявки приходят в отдел из АИС.
React-приложение не должно формировать DOCX и не должно показывать кнопки
«Сформировать документ» или «Сформировать дополнительное соглашение».
Маршрута генерации на сервере нет; обращение к прежнему адресу
`GET /contracts/{id}/agreement` возвращает `404`.

Файлы документов пользователь только загружает в единый блок файлов как
`signed_scan` (подписанный скан) или `source_file` (исходник от организации).
Причина: система хранит и учитывает документы, полученные из АИС, но не
является средством их подготовки.

## 2. Контракты API

### 2.0. Окружение разработки

Подъём бэкенда:

```bash
git clone <адрес-репозитория-бэкенда> doc-bntu
cd doc-bntu
docker-compose up --build -d
```

Старый интерфейс и API доступны на `http://localhost:8000`, React dev-server
— на `http://localhost:3000`.

Фиксированных тестовых паролей в репозитории нет. Учётные записи
`admin/admin` и `head/admin` удалены. На чистой базе открыть
`http://localhost:8000/setup` и создать администратора с паролем не короче
8 символов. Логин и пароль, созданные разработчиком на этом экране,
используются для проверки API.

Проверка сессии через `curl`:

```bash
curl -i -c cookies.txt \
  -H "Content-Type: application/json" \
  -d '{"username":"my-admin","password":"my-test-password"}' \
  http://localhost:8000/api/auth/login

curl -i -b cookies.txt http://localhost:8000/api/auth/me

curl -i -b cookies.txt -X POST http://localhost:8000/api/auth/logout
```

Для dev-режима сервер разрешает origin `http://localhost:3000` с
`credentials=True`. Значение `Access-Control-Allow-Origin` должно быть точным,
не `*`. В production React и API работают с одного origin, CORS не нужен.

### 2.1. Общие соглашения

- Все `/api/*`, кроме `POST /api/auth/login` и `GET /api/health`, требуют
  действующую session-cookie `session`.
- Формат обычных запросов и ответов — `application/json; charset=utf-8`.
- Исключение — импорт: `multipart/form-data`.
- JSON кодируется в UTF-8; кириллица не превращается в `\uXXXX`.
- `date` передаётся как `YYYY-MM-DD`, например `"2030-12-31"`.
- `datetime` передаётся в ISO 8601 с часовым поясом, например
  `"2026-09-22T13:13:01.873632+00:00"`.
- Отсутствующее значение передаётся как `null`, а не как пустая строка.
- Роли: `ADMIN` — администратор, `HEAD` — руководитель отдела.
- Все списки принимают `page` и `per_page`. По умолчанию `page=1`,
  `per_page=50`; максимальное `per_page=100`.

Единая оболочка списка:

```json
{
  "items": [],
  "total": 0,
  "page": 1,
  "per_page": 50
}
```

Единый формат ошибки:

```json
{
  "detail": "Текст ошибки"
}
```

Для ошибок проверки входных данных ответ `422 Unprocessable Entity` содержит
детали по каждому полю:

```json
{
  "detail": [
    {
      "field": "date_start",
      "message": "Поле обязательно",
      "code": "required"
    },
    {
      "field": "date_end",
      "message": "Дата окончания не может быть раньше даты начала",
      "code": "invalid_date_range"
    }
  ]
}
```

`field` совпадает с именем поля JSON или параметра запроса. Для общей ошибки,
не связанной с одним полем, используется `field: null`. Формат с одной строкой
`{"detail": "..."}` сохраняется для ошибок `400`, `401`, `403`, `404` и
`409`.

Коды:

- `400` — операция противоречит бизнес-правилу;
- `401` — нет действующей сессии;
- `403` — роль не имеет доступа;
- `404` — объект не найден;
- `409` — конфликт уникальности или состояния;
- `422` — неверный формат или обязательное поле.

### 2.2. Авторизация

#### `POST /api/auth/login`

Доступ: без сессии.

Запрос:

```json
{
  "username": "admin",
  "password": "my-test-password"
}
```

Ответ `200 OK`; одновременно устанавливается HttpOnly session-cookie:

```json
{
  "id": 1,
  "username": "admin",
  "full_name": "Иванов Иван Иванович",
  "role": "ADMIN",
  "need_password_change": false
}
```

Ошибки: `401` — неверный логин/пароль или неактивная учётная запись;
`422` — отсутствует логин либо пароль.

#### `POST /api/auth/logout`

Доступ: вошедший пользователь. Тело отсутствует.

Ответ: `204 No Content`; session-cookie очищается.

Ошибка: `401` — сессия уже отсутствует или недействительна.

#### `GET /api/auth/me`

Доступ: обе роли. Это источник данных вкладки «Профиль» в личном кабинете.
ФИО, логин и роль отображаются только для чтения; отдельного запроса для их
самостоятельного редактирования нет.

Ответ `200 OK`:

```json
{
  "id": 1,
  "username": "admin",
  "full_name": "Иванов Иван Иванович",
  "role": "ADMIN",
  "need_password_change": false
}
```

Ошибка: `401` — нет действующей сессии.

#### `POST /api/auth/change-password`

Доступ: обе роли, включая пользователя с
`need_password_change=true`.

Запрос:

```json
{
  "current_password": "temporary-password",
  "new_password": "new-password-2026"
}
```

Поле «Повтор нового пароля» существует только в React-форме. Перед отправкой
React проверяет совпадение; в JSON это поле не включается.

Ответ: `204 No Content`.

Ошибки: `400` — текущий пароль неверен; `401` — нет сессии; `422` — новый
пароль короче 8 символов.

После успеха старый пароль не действует, `need_password_change` становится
`false`. Пароль и его хеш никогда не возвращаются в JSON и не записываются в
diff аудита.

### 2.9. Импорт Excel

#### `POST /api/import`

Доступ: обе роли. Тип запроса: `multipart/form-data`; единственное поле
`file`, формат `.xlsx`.

Пример:

```bash
curl -b cookies.txt \
  -F "file=@МТЗ-из базы.xlsx" \
  http://localhost:8000/api/import
```

Ответ `200 OK` после первоначальной загрузки файла МТЗ:

```json
{
  "rows": 60,
  "organizations": 1,
  "contracts": 1,
  "faculties": 11,
  "specialties": 60,
  "organizations_created": 1,
  "contracts_created": 1,
  "faculty_links_created": 11,
  "order_items_created": 60,
  "specialties_created": null,
  "specialties_updated": null
}
```

Первые девять числовых показателей соответствуют текущему результату
`ImportResult`. Раздельные счётчики `specialties_created` и
`specialties_updated` текущий импортёр не собирает, поэтому их контракт —
**уточним**; до реализации сервер возвращает `null`, а фронтенд их не
показывает.

Повторный импорт того же файла обновляет существующие записи и не создаёт
дубликаты. Поэтому `organizations_created`, `contracts_created`,
`faculty_links_created` и `order_items_created` при повторе могут быть равны
нулю, а `rows`, `organizations`, `contracts`, `faculties` и `specialties`
останутся показателями обработанного файла.

Ошибки: `401`; `400` — файл не `.xlsx`; `422` — отсутствует файл или в нём
нет обязательных колонок/есть неверное значение потребности; `500` —
непредвиденная ошибка чтения, при которой вся операция и аудит откатываются.

### 2.10. Статистика и экспорт (DRAFT)

#### `GET /api/statistics`

Доступ: обе роли. Ответ содержит четыре показателя по организациям:

- `total` — всего уникальных организаций;
- `with_contracts` — организации, у которых есть хотя бы один договор;
- `with_applications` — организации, у которых есть хотя бы одна заявка;
- `with_contracts_and_applications` — организации, у которых есть документы
  обоих типов.

Организация считается один раз по своему `id`, даже если у неё несколько
договоров, заявок или факультетов. Необязательный `faculty_id` ограничивает
все четыре показателя организациями, документы которых относятся к выбранному
факультету.

Статистика по всему отделу:

```http
GET /api/statistics
```

```json
{
  "faculty": null,
  "organizations": {
    "total": 14,
    "with_contracts": 11,
    "with_applications": 5,
    "with_contracts_and_applications": 2
  }
}
```

Тот же ответ с фильтром по факультету:

```http
GET /api/statistics?faculty_id=1
```

```json
{
  "faculty": {
    "id": 1,
    "name": "Автотракторный"
  },
  "organizations": {
    "total": 3,
    "with_contracts": 2,
    "with_applications": 2,
    "with_contracts_and_applications": 1
  }
}
```

Значения в примерах показывают формат ответа, а не фиксированные данные
рабочей базы. Ошибки: `401`; `422` — факультет не существует или параметр
имеет неверный формат.

#### `GET /export/contracts`

Доступ: обе роли. Параметры совпадают с `GET /api/contracts`: `q`,
`faculty_id`, `status`, `end_year`, `urgency`. Экспортируется вся текущая
выборка без пагинации.

```bash
curl -b cookies.txt \
  --output contracts.xlsx \
  "http://localhost:8000/export/contracts?faculty_id=1&status=Активен"
```

Ответ `200 OK`: MIME-тип
`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`, заголовок
`Content-Disposition: attachment; filename="contracts.xlsx"` и бинарный XLSX.

#### `GET /export/applications`

Доступ: обе роли. Параметры совпадают с `GET /api/applications`: `q`,
`faculty_id`, `status`. Экспортируется вся текущая выборка без пагинации.

```bash
curl -b cookies.txt \
  --output applications.xlsx \
  "http://localhost:8000/export/applications?faculty_id=1&status=Заявка"
```

Ответ имеет тот же MIME-тип; имя файла — `applications.xlsx`. Для обоих
экспортов ошибки: `401`; `422` — неверный фильтр.

## 3. Порядок совместной работы

### Фронтенд

1. Исправить авторизацию, статусы, роли и базовый HTTP-клиент по части 1.
2. Удалить все демонстрационные данные и локальные справочники.
3. STABLE-эндпоинты подключать к живому API; для DRAFT использовать типы и
   моки строго по зафиксированным форматам.
4. Если эндпоинт помечен «уточним», скрыть действие или оставить явно
   отключённым; не имитировать сохранение локально.
5. Запускать React на `http://localhost:3000/app/` против FastAPI на
   `http://localhost:8000`.

### Бэкенд

1. Реализовать JSON-маршруты `/api/*` как тонкий слой над существующими
   сервисами и репозиториями.
2. Не дублировать бизнес-правила в API-обработчиках.
3. Сохранить старые Jinja2-страницы без перенаправления: они остаются
   резервным интерфейсом.
4. Настроить CORS для `http://localhost:3000` в dev-режиме и раздачу сборки
   React по `/app` в production.

### Точка синхронизации

Совместная проверка проводится в следующем порядке:

1. Вход настоящим логином и паролем; обновление страницы сохраняет сессию.
2. Реестр организаций показывает МТЗ из PostgreSQL: одну организацию, один
   договор и 11 строк-представлений по факультетам.
3. В строке Автотракторного факультета показаны только его специальности.
4. Переход открывает карточку организации по фактическому ID.
5. Журнал показывает реальные события, ФИО вошедшего сотрудника и читаемый
   `diff`.
6. Выход завершает серверную сессию; повторный `GET /api/auth/me` возвращает
   `401`.

Интеграция считается завершённой только после прохождения всех шести пунктов
без демонстрационных данных и локальной имитации операций.

## 4. Swagger

Интерактивная документация доступна по адресу
[http://localhost:8000/docs](http://localhost:8000/docs), исходная OpenAPI-схема
— по адресу
[http://localhost:8000/openapi.json](http://localhost:8000/openapi.json).

### Как авторизоваться

1. На чистой базе сначала создать администратора через старую страницу
   `http://localhost:8000/setup`.
2. Открыть Swagger, раскрыть группу `auth` и выбрать
   `POST /api/auth/login`.
3. Нажать **Try it out**, указать настоящий логин и пароль, затем выполнить
   запрос.
4. Ответ `200` устанавливает HttpOnly cookie `session`. Браузер Swagger
   сохранит её и автоматически приложит к следующим запросам того же origin.
5. Выполнить `GET /api/auth/me`: ответ `200` и данные сотрудника подтверждают,
   что сессия работает.
6. Для завершения сессии выполнить `POST /api/auth/logout`.

Кнопка **Authorize** документирует схему `cookieAuth` и имя cookie. Вручную
вводить или копировать подписанное значение cookie не нужно: HttpOnly cookie
создаётся только сервером через `POST /api/auth/login`.

### Готовность групп

| Группа | Что можно проверять сейчас |
| --- | --- |
| `auth` | `login`, `logout`, `me`, `change-password` — готовы к интерактивной проверке |
| `organizations` | Появится в Swagger после реализации соответствующих JSON-маршрутов из части 2 |
| `contracts` | Появится после реализации JSON-реестра и карточки договора |
| `applications` | Появится после реализации JSON-реестра и карточки заявки |
| `orders` | Появится после реализации чтения редакции заказа |
| `audit` | Появится после реализации JSON-реестра журнала |
| `users` | Появится после реализации административных JSON-маршрутов |
| `settings` | `GET /api/auth/me` и `POST /api/auth/change-password` готовы для личного кабинета обеих ролей; реквизитов БНТУ и отдельных `GET/PUT /api/settings` не будет |
| `import-export` | JSON-импорт появится после реализации; экспорт договоров и заявок зафиксирован как DRAFT |

Служебный `GET /api/health`, старые HTML-страницы и внутренние редиректы в
OpenAPI-схему не включаются. При `SHOW_DOCS=false` адрес `/docs` возвращает
`404`; `/openapi.json` остаётся машинно-читаемым источником актуальной схемы.

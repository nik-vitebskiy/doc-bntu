# Спецификация интеграции React-интерфейса с системой «Кадровый заказ»

Дата фиксации контракта: 24.09.2026.

Документ предназначен для разработчика React-приложения из репозитория
`Daniil-opin/doc-bntu-front`, каталог `frontend`. Он описывает обязательные
изменения фронтенда и целевой JSON-контракт FastAPI.

На дату документа серверные страницы Jinja2 работают, но маршруты `/api/*`
ещё не реализованы. Команда бэкенда добавляет их параллельно с переделкой
React-приложения. Нельзя подменять указанные ниже JSON-маршруты существующими
HTML-маршрутами без `/api`: HTML-маршруты возвращают страницы или HTTP 303,
а не описанные здесь объекты.

Все значения в примерах соответствуют полям действующих моделей проекта.
Массивы в больших ответах сокращены до нескольких элементов, но каждый
показанный элемент приведён полностью по контракту.

## 1. Что исправить в React-приложении

### 1.1. Авторизация

#### `frontend/src/app/providers.tsx`

- **Сейчас:** пользователь определяется по `localStorage['bntu-auth']`, любой
  непустой пароль считается правильным, после входа создаётся локальный
  `demoUser` с ролью `ADMIN`.
- **Должно стать:** при запуске вызвать `GET /api/auth/me`; при входе отправить
  логин и пароль в `POST /api/auth/login`; хранить пользователя и его роль из
  ответа сервера. `localStorage` не является признаком действующей сессии.
- **Зачем:** автором изменений в журнале должен быть реально вошедший
  сотрудник.

Вызовы выполнять с `credentials: 'include'`. JWT и заголовок `Authorization`
не используются.

#### `frontend/src/pages/LoginPage.tsx`

- **Сейчас:** поля заранее заполнены `admin/admin`; вход выполняется локально;
  есть восстановление пароля по электронной почте.
- **Должно стать:** поля пустые; форма вызывает `POST /api/auth/login`;
  восстановление пароля и весь экран отправки письма удалить.
- **Зачем:** в модели пользователя нет электронной почты, сброс пароля
  выполняет администратор.

После успешного входа:

1. Если `need_password_change === false`, перейти на `/app/`.
2. Если `need_password_change === true`, перейти на
   `/app/change-password` и не открывать остальные защищённые страницы до
   успешной смены пароля.

#### Новый экран `/app/change-password`

- Поля: текущий пароль, новый пароль, повтор нового пароля.
- Минимальная длина нового пароля — 8 символов.
- Вызов: `POST /api/auth/change-password`.
- После успеха повторно вызвать `GET /api/auth/me`, затем перейти на `/app/`.

#### `frontend/src/shared/ui/AppShell.tsx`

- **Сейчас:** выход очищает только локальное состояние.
- **Должно стать:** вызвать `POST /api/auth/logout`, затем очистить локальное
  состояние, удалить оставшийся от прототипа ключ `bntu-auth` из
  `localStorage` и перейти на `/app/login`. После миграции не записывать
  признаки авторизации в `localStorage` повторно.
- **Зачем:** серверная сессия также должна завершиться.

#### `frontend/src/shared/api/client.ts`

- При любом ответе `401` очистить локального пользователя и перейти на
  `/app/login`.
- При `403` показать сообщение «Недостаточно прав для выполнения действия»;
  приложение не должно падать или считать операцию успешной.
- Не считать HTML после перенаправления успешным JSON-ответом. Для `/api/*`
  сервер возвращает JSON или `204 No Content`, но не HTML.

### 1.5. Импорт Excel

Не устанавливать `Content-Type: application/json` глобально для всех

```ts
const headers = new Headers(init?.headers)
if (!(init?.body instanceof FormData) && !headers.has('Content-Type')) {
  headers.set('Content-Type', 'application/json')
}
```

Для `FormData` браузер сам установит `multipart/form-data` с корректной
границей частей.

- Отправлять файл полем `file` в `POST /api/import`.

## 2. Контракты API

### 2.0. Окружение разработки

Подъём бэкенда:

```bash
git clone <адрес-репозитория-бэкенда> doc-bntu
cd doc-bntu
docker-compose up --build -d
```

Старый интерфейс и API доступны на `http://localhost:8000`, React dev-server
— на `http://localhost:3000`.

Фиксированных тестовых паролей в репозитории нет. Учётные записи
`admin/admin` и `head/admin` удалены. На чистой базе открыть
`http://localhost:8000/setup` и создать администратора с паролем не короче
8 символов. Логин и пароль, созданные разработчиком на этом экране,
используются для проверки API.

Проверка сессии через `curl`:

```bash
curl -i -c cookies.txt \
  -H "Content-Type: application/json" \
  -d '{"username":"my-admin","password":"my-test-password"}' \
  http://localhost:8000/api/auth/login

curl -i -b cookies.txt http://localhost:8000/api/auth/me

curl -i -b cookies.txt -X POST http://localhost:8000/api/auth/logout
```

Для dev-режима сервер разрешает origin `http://localhost:3000` с
`credentials=True`. Значение `Access-Control-Allow-Origin` должно быть точным,
не `*`. В production React и API работают с одного origin, CORS не нужен.

### 2.1. Общие соглашения

- Все `/api/*`, кроме `POST /api/auth/login` и `GET /api/health`, требуют
  действующую session-cookie `session`.
- Формат обычных запросов и ответов — `application/json; charset=utf-8`.
- Исключение — импорт: `multipart/form-data`.
- JSON кодируется в UTF-8; кириллица не превращается в `\uXXXX`.
- `date` передаётся как `YYYY-MM-DD`, например `"2030-12-31"`.
- `datetime` передаётся в ISO 8601 с часовым поясом, например
  `"2026-09-22T13:13:01.873632+00:00"`.
- Отсутствующее значение передаётся как `null`, а не как пустая строка.
- Роли: `ADMIN` — администратор, `HEAD` — руководитель отдела.
- Все списки принимают `page` и `per_page`. По умолчанию `page=1`,
  `per_page=50`; максимальное `per_page=100`.

Единая оболочка списка:

```json
{
  "items": [],
  "total": 0,
  "page": 1,
  "per_page": 50
}
```

Единый формат ошибки:

```json
{
  "detail": "Текст ошибки"
}
```

Коды:

- `400` — операция противоречит бизнес-правилу;
- `401` — нет действующей сессии;
- `403` — роль не имеет доступа;
- `404` — объект не найден;
- `409` — конфликт уникальности или состояния;
- `422` — неверный формат или обязательное поле.

### 2.2. Авторизация

#### `POST /api/auth/login`

Доступ: без сессии.

Запрос:

```json
{
  "username": "admin",
  "password": "my-test-password"
}
```

Ответ `200 OK`; одновременно устанавливается HttpOnly session-cookie:

```json
{
  "id": 1,
  "username": "admin",
  "full_name": "Иванов Иван Иванович",
  "role": "ADMIN",
  "need_password_change": false
}
```

Ошибки: `401` — неверный логин/пароль или неактивная учётная запись;
`422` — отсутствует логин либо пароль.

#### `POST /api/auth/logout`

Доступ: вошедший пользователь. Тело отсутствует.

Ответ: `204 No Content`; session-cookie очищается.

Ошибка: `401` — сессия уже отсутствует или недействительна.

#### `GET /api/auth/me`

Доступ: вошедший пользователь.

Ответ `200 OK`:

```json
{
  "id": 1,
  "username": "admin",
  "full_name": "Иванов Иван Иванович",
  "role": "ADMIN",
  "need_password_change": false
}
```

Ошибка: `401` — нет действующей сессии.

#### `POST /api/auth/change-password`

Доступ: вошедший пользователь, включая пользователя с
`need_password_change=true`.

Запрос:

```json
{
  "current_password": "temporary-password",
  "new_password": "new-password-2026"
}
```

Ответ: `204 No Content`.

Ошибки: `400` — текущий пароль неверен; `401` — нет сессии; `422` — новый
пароль короче 8 символов.

После успеха старый пароль не действует, `need_password_change` становится
`false`. Пароль и его хеш никогда не возвращаются в JSON и не записываются в
diff аудита.

### 2.9. Импорт Excel

#### `POST /api/import`

Доступ: обе роли. Тип запроса: `multipart/form-data`; единственное поле
`file`, формат `.xlsx`.

Пример:

```bash
curl -b cookies.txt \
  -F "file=@МТЗ-из базы.xlsx" \
  http://localhost:8000/api/import
```

Ответ `200 OK` после первоначальной загрузки файла МТЗ:

```json
{
  "rows": 60,
  "organizations": 1,
  "contracts": 1,
  "faculties": 11,
  "specialties": 60,
  "organizations_created": 1,
  "contracts_created": 1,
  "faculty_links_created": 11,
  "order_items_created": 60,
  "specialties_created": null,
  "specialties_updated": null
}
```

Первые девять числовых показателей соответствуют текущему результату
`ImportResult`. Раздельные счётчики `specialties_created` и
`specialties_updated` текущий импортёр не собирает, поэтому их контракт —
**уточним**; до реализации сервер возвращает `null`, а фронтенд их не
показывает.

Повторный импорт того же файла обновляет существующие записи и не создаёт
дубликаты. Поэтому `organizations_created`, `contracts_created`,
`faculty_links_created` и `order_items_created` при повторе могут быть равны
нулю, а `rows`, `organizations`, `contracts`, `faculties` и `specialties`
останутся показателями обработанного файла.

Ошибки: `401`; `400` — файл не `.xlsx`; `422` — отсутствует файл или в нём
нет обязательных колонок/есть неверное значение потребности; `500` —
непредвиденная ошибка чтения, при которой вся операция и аудит откатываются.

```json
  "status": "ok"
}
```

Ответ `200` означает, что FastAPI доступен. Этот маршрут не подтверждает
наличие пользовательской сессии; для этого используется `/api/auth/me`.

## 3. Порядок совместной работы

### Фронтенд

1. Исправить авторизацию, статусы, роли и базовый HTTP-клиент по части 1.
2. Удалить все демонстрационные данные и локальные справочники.
3. Подключать только эндпоинты с зафиксированным контрактом из части 2.
4. Если эндпоинт помечен «уточним», скрыть действие или оставить явно
   отключённым; не имитировать сохранение локально.
5. Запускать React на `http://localhost:3000/app/` против FastAPI на
   `http://localhost:8000`.

### Бэкенд

1. Реализовать JSON-маршруты `/api/*` как тонкий слой над существующими
   сервисами и репозиториями.
2. Не дублировать бизнес-правила в API-обработчиках.
3. Сохранить старые Jinja2-страницы без перенаправления: они остаются
   резервным интерфейсом.
4. Настроить CORS для `http://localhost:3000` в dev-режиме и раздачу сборки
   React по `/app` в production.

### Точка синхронизации

Совместная проверка проводится в следующем порядке:

1. Вход настоящим логином и паролем; обновление страницы сохраняет сессию.
2. Реестр организаций показывает МТЗ из PostgreSQL: одну организацию, один
   договор и 11 строк-представлений по факультетам.
3. В строке Автотракторного факультета показаны только его специальности.
4. Переход открывает карточку организации по фактическому ID.
5. Журнал показывает реальные события, ФИО вошедшего сотрудника и читаемый
   `diff`.
6. Выход завершает серверную сессию; повторный `GET /api/auth/me` возвращает
   `401`.

Интеграция считается завершённой только после прохождения всех шести пунктов
без демонстрационных данных и локальной имитации операций.
